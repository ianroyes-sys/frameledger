## Deployment prerequisites and launch blockers

Set Whop API key, webhook signing secret, environment and scoped connected-account approval. Provision each trusted business-to-Whop account mapping server-side after ownership is verified. Do not let a client submit an arbitrary Whop account ID. Verify provider version with sandbox fixtures, real webhook signature deliveries, amount formats, paid/refunded states, account-level permissions, and settlement transitions. Mock tests verify our contract, not upstream availability.

No FDIC/pass-through insurance, interest, bank charter, SIPC, guaranteed yield, or legal fund segregation is claimed. KYC approval in a browser callback alone must never authorize real money movement.

## Pending invoice recovery

If the provider request has unknown outcome, do not resend blindly. An authorized operator checks Whop dashboard/API invoices for the exact customer, amount, description, and time. If a matching invoice exists, write its verified external ID to the existing `invoice_metadata` row, set state to sent, and invoke reconciliation. If the provider confirms no resource exists, clear the pending metadata row and explicitly retry the send. Record the recovery in audit_logs. Missing credentials are checked before the durable operation is created. This deliberately requires operator verification because legacy invoice idempotency coverage is not established. No automatic money retries are implemented.

## Contractor transfer implementation

A prepared, disabled-by-default ledger-transfer implementation now exists at `/api/collaborators/pay` and `src/server/transfers.ts`, using the verified current [create](https://docs.whop.com/api-reference/beta/transfers/create-transfer) and [retrieve](https://docs.whop.com/api-reference/beta/transfers/retrieve-transfer) contracts. It does not add external bank payouts or crypto sends. Verified destination bindings are maintained in `collaborator_payout_destinations`, inaccessible to browser writes. Set `WHOP_PAYOUTS_ENABLED` and publish the verified `WHOP_TRANSFER_FEE_DISCLOSURE` only after the deployment prerequisites are satisfied. Transfer status uses exactly processing/succeeded/failed; succeeded, never a pending response, records payment.

Recovery: inspect the persisted operation's original origin/destination/amount/key. Within 23 hours the worker retries the same current-API request with the same key. If an external transfer ID is recovered after a timeout, verify its canonical fields before attaching it to the operation. Beyond the request-retention window, do not create a new transfer automatically. Failed transfers remain tracked because Whop may retry the same transfer ID. Contact the provider and confirm final outcome before releasing or replacing an operation. No raw financial call was executed during development.
